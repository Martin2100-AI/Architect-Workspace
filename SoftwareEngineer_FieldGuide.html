Software Engineer Field Guide

For AI Solution Architects who direct, evaluate, and approve AI-generated code — not for engineers who write every line by hand. This guide teaches the ~20% of software engineering that determines whether an AI-built system is trustworthy, and applies it end-to-end to one worked example.

Worked example used throughout this guide: Insurance — ClaimSight, an AI-assisted claims triage and fraud risk-scoring feature for a mid-size property & casualty insurer. Why Software Engineering Exists

Anyone can write code that runs once, on one machine, for one demo. Software engineering is the discipline that makes code survive contact with reality: other engineers who didn’t write it, users who misuse it, load it wasn’t sized for, and changes made under deadline pressure two years from now.

That discipline matters more, not less, when an LLM writes the first draft. An AI code generator is extraordinarily good at producing plausible, locally-correct code quickly. It is not accountable for the system it just changed, has no memory of the trade-off it made six files ago, and cannot be paged at 2 a.m. when a claim silently double-pays a policyholder. That accountability gap is exactly the seat an AI Solution Architect fills.

What AI code generation is good at

  • Producing a correct-looking implementation fast
  • Following an explicit, well-specified contract
  • Writing boilerplate, tests, and repetitive patterns
  • Explaining what code does when asked

What still requires a human architect

  • Deciding the contract in the first place
  • Judging blast radius and reversibility
  • Catching a plausible-but-wrong design before it ships
  • Owning the trade-off when two good options conflict

The remaining sections of Part A cover the specific 20% of engineering knowledge that lets you do that job: read a design before it’s built, recognize a contract violation, tell disciplined modularity from over-engineering, and know what “done” objectively means.

Technical Design Documents

A Technical Design Document (TDD) is the artifact that turns a feature request into an engineering plan before code is written. Its job is to force the hard decisions — data model, module boundaries, failure modes, trade-offs — into writing where they can be reviewed cheaply, instead of discovering them mid-implementation where they are expensive to reverse.

Architect’s rule: if an AI agent proposes an implementation with no design document behind it, the design document is missing, not unnecessary. Ask for it before reviewing the code. A TDD is cheap to reject; a merged PR is not.

A complete TDD answers, in order: what problem is this solving and for whom (context), what approach was chosen and what alternatives were rejected and why, how the system decomposes into modules, what the data model looks like, what the sequence of events is for the primary flow, and what could go wrong. See ClaimSight’s TDD in Part B for a complete worked example.

Modularity & Separation of Concerns

A module should have one reason to change. When a “claims service” both scores fraud risk and formats email templates, a change to the email template risks breaking fraud scoring — two unrelated concerns now share a blast radius they shouldn’t share.

SmellWhy it mattersWhat good looks like
A module named for one thing does another (claimValidator.ts that also sends notifications)Reviewers can’t predict blast radius from the filenameOne responsibility per module; the name is a promise
Circular imports (A imports B imports A)Signals a missing shared abstraction; makes both modules untestable in isolationExtract the shared piece into module C; A and B both depend on C
A module imports from 15+ internal modulesIt is almost certainly doing too muchSplit along the seams where responsibilities diverge
Business logic embedded inside a route handlerLogic can’t be unit-tested without spinning up HTTPRoute handlers parse/validate and delegate; services hold logic

In the ClaimSight example, this is why Feature Extraction, Risk Scoring, and Routing are three separate modules rather than one “triage engine” — each has an independent reason to change (a new feature signal, a new scoring model version, a new business rule), and each can be tested and reasoned about alone. See Module & Component Design.

Interfaces & Contracts

A contract is the promise a module makes about its inputs, its outputs, and the ways it can fail — stated explicitly enough that the caller never has to read the implementation to use it safely. This is the single most important lens for reviewing AI-generated code: an implementation can be internally elegant and still violate its contract, and elegance is what an AI reviewer (human or model) notices first.

What a real contract specifies: typed inputs, typed outputs (including the shape of errors), the explicit list of exceptions/error classes it can throw, whether it is idempotent, and its timeout/retry behavior at any external boundary. If any of these five is undocumented, the contract is incomplete — approve nothing against it.

Example from ClaimSight — the Risk Scoring Client’s contract is not just “takes features, returns a score.” It is: scoreClaim(features: ClaimFeatureVector): Promise<RiskAssessmentResult>, times out at 8 seconds, retries twice with exponential backoff on UpstreamUnavailable, trips a circuit breaker after 5 consecutive failures, and never throws a generic Error — only ScoringTimeoutError or ScoringServiceUnavailableError. A caller can build correct failure handling from that sentence alone, without reading the client’s source. Full signatures in Module & Component Design.

Clean Code & Naming

Code is read far more often than it is written, and an AI agent generates a first draft in seconds where a name choice is often arbitrary unless directed. Names are the cheapest, highest-leverage thing an architect can insist on.

PrincipleBadGood
Name reveals intentprocess(x)scoreClaimFraudRisk(features)
No abbreviations that need a legendcalcAdjRsk(c, p)calculateAdjustedRiskScore(claim, policy)
Booleans read as questionsflagisHighRiskClaim
Constants are named, not magicif (score > 70)if (score > SIU_ESCALATION_THRESHOLD)

Size discipline is part of clean code, not separate from it: this repository’s house limits are a soft target of ~300 lines / hard ceiling of 500 per file, and ~50/100 lines per function. A function that needs three screens to read cannot be reviewed — only skimmed.

Version Control: Branching & Code Review

Version control is the system of record for why code changed, not just what changed. Two disciplines make it work: small, reviewable units of change, and a review gate that actually catches problems before merge.

  • Branch per unit of work, named so its purpose is visible in a list of thirty branches (feature/CS-118-siu-threshold, not fix-stuff).
  • Small pull requests. A 1,200-line PR is not reviewed, it is rubber-stamped. Target under ~400 lines of diff.
  • Review is a gate, not a formality. At minimum: does it match its stated contract, does it have tests for failure paths, does it introduce a governance-boundary risk.
  • Squash-merge with a message that explains why, so git log reads as a decision history, not a diary of typo fixes.

See Branching & Pull-Request Workflow for ClaimSight’s concrete rules, including a git-flow diagram.

The Testing Pyramid

Tests are not evidence a feature might work — they are the mechanism by which correctness claims become checkable instead of trusted. The pyramid shape matters as much as the presence of tests: unit tests are cheap and fast, so most of your coverage should live there; end-to-end tests are slow and flaky, so they should be reserved for the handful of flows where nothing less will do.

Unit — ~70%

Pure logic in isolation. No network, no database. A feature-extraction formula, a routing-rule evaluator, a validator. Runs in milliseconds.

Integration — ~20%

A module talking to a real (dev/sandbox) dependency — a test database, a mocked external API, a message queue. Confirms the wiring, not just the logic.

End-to-End — ~10%

A real browser or client driving the full stack for the flows that matter most — claim submission through triage assignment, in ClaimSight’s case.

A shipped feature must clear four kinds of case, not just the demo path: happy path, failure path (dependency down, malformed input, missing auth), boundary cases (empty, max-length, off-by-one), and idempotency (same operation run twice yields the same end state). See ClaimSight’s Test Plan for all four applied to every module.

Technical Debt

Technical debt is a deliberate or accidental shortcut that trades long-term maintainability for short-term speed — a real financial metaphor: it can be taken on knowingly (a fast, ugly fix to hit a deadline) or accrue unknowingly (a pattern that was fine at low volume and breaks at scale). Either way it accrues interest: every future change in that area costs more than it should.

The architect’s job is not to eliminate debt — it is to make it visible and priced. An AI agent will happily generate a quick, debt-laden fix if asked for one; it will not flag that the fix is debt unless the review process asks the question explicitly. “It works in dev, we’ll fix it later” with no ticket and no owner is how debt becomes invisible.

Signals worth escalating: a grandfathered oversize file touched again without being split, a workaround comment with no linked follow-up, a AI-generated PR that duplicates logic that already exists elsewhere in the codebase (see DRY, next section).

DRY & SOLID (Lightly)

DRY — Don’t Repeat Yourself. When the same non-trivial logic appears in three places, it should live in one. Two is sometimes coincidence; three is a pattern. Applied to ClaimSight: the rule that decides “is this claim amount within fast-track eligibility” must exist in exactly one function, called from intake preview, routing, and reporting — not copied three times with three chances to drift apart.

SOLID, in one line each, as an architect needs it — not as an engineer needs to implement it:

PrincipleWhat to look for when reviewing
S — Single ResponsibilityOne reason to change per module (see Modularity above)
O — Open/ClosedNew routing rule added without editing the core routing engine’s control flow
L — Liskov SubstitutionA mock Risk Scoring Client in tests behaves like the real one from the caller’s perspective
I — Interface SegregationNotification Service doesn’t force callers to depend on SMS-only methods they never use
D — Dependency InversionRouting Engine depends on a RiskAssessmentResult type, not on the scoring vendor’s SDK directly

Error Handling

The single most common defect in AI-generated code that otherwise looks production-ready is a silently swallowed error — try { ... } catch (e) {}, or a generic catch (Error) that masks which specific thing failed. Both look clean in a diff and both turn a debuggable failure into a mystery at 2 a.m.

Forbidden patternWhy it’s a defectRequired instead
Silent catchFailure vanishes; nothing alerts, nothing logsLog with a stable error_class, re-throw or handle explicitly
Generic catch (Error)Masks whether it was a timeout, a validation failure, or a bugSpecific error classes: ScoringTimeoutError, ValidationError, etc.
Unbounded retryCan hang a request or hammer a failing dependency foreverCapped attempts with backoff, then circuit-break
No timeout on an external callOne slow dependency can hang the whole request chainExplicit timeout on every HTTP/DB/queue call

Every external boundary must answer four questions, in writing: what happens if this fails, will it retry and how, what is the recovery path once retries are exhausted, and what failure modes are explicitly out of scope. See ClaimSight’s TDD § Risks & Trade-offs for these answered against the Risk Scoring Service dependency specifically.

Good Code vs. Bad Code

The same function, two ways — the AI-generated first draft you should reject, and the version an architect should require before approving the PR. Both “work” on the happy path. Only one is safe to ship.

Reject — looks done, isn’t

async function scoreClaim(f) {
  try {
    const r = await fetch(SCORING_URL, {
      method: 'POST',
      body: JSON.stringify(f)
    });
    const data = await r.json();
    if (data.score > 70) {
      data.queue = 'siu';
    } else {
      data.queue = 'standard';
    }
    return data;
  } catch (e) {
    return { score: 0, queue: 'standard' };
  }
}
  • No timeout — one slow call hangs the request
  • No retry / no circuit breaker
  • any-shaped input and output, no contract
  • Magic number 70 instead of a named threshold
  • Silent catch masks failure as a fake “standard” score — a real fraud case could be waved through as low-risk

Approve — contract-safe

const SIU_ESCALATION_THRESHOLD = 70;
const SCORING_TIMEOUT_MS = 8000;

async function scoreClaim(
  features: ClaimFeatureVector
): Promise<RiskAssessmentResult> {
  const res = await callWithTimeout(
    () => scoringClient.score(features),
    SCORING_TIMEOUT_MS
  ).catch((e) => {
    throw classifyScoringError(e);
    // ScoringTimeoutError | ScoringServiceUnavailableError
  });

  const triage = res.riskScore >= SIU_ESCALATION_THRESHOLD
    ? 'SIU_QUEUE'
    : 'STANDARD_ADJUSTER_QUEUE';

  logScoringEvent({ correlationId, res, triage });
  return { ...res, triageRecommendation: triage };
}
  • Explicit timeout, explicit typed contract in/out
  • Named threshold, no magic numbers
  • Specific, classified error types — failure surfaces, doesn’t hide
  • Structured, correlation-traceable logging

The Architect’s Review Lens

A structured order in which to evaluate any AI-generated pull request, before approving it. Work top to bottom — each layer catches a class of defect the next layer can’t.

  1. Contract match. Does the implementation match the module’s declared inputs, outputs, and error types — not just “does it run”?
  2. Failure paths present. Timeout, retry, and a named failure mode for every external call. No silent catches.
  3. Idempotency. If this can be retried or resubmitted, does the second run produce the same end state as the first?
  4. Blast radius. If this is wrong, what breaks, how far does it spread, and is it reversible?
  5. Test coverage of the four required cases. Happy path, failure path, boundary, idempotency — not just the demo.
  6. Naming & size. Can a junior developer understand this in one read? Does it respect file/function size ceilings?
  7. Duplication. Does this reinvent logic that already exists elsewhere in the codebase?
  8. Governance boundary check. Does this touch schema, compliance, external paid dependencies, or production infrastructure — and if so, has it been escalated?
If all eight pass: approve. If any fail: it is not “approve with comments” — a broken contract or a missing failure path is a blocking finding, not a nitpick.

1. Context

Meridian Assurance receives approximately 4,200 property & casualty claims per week across web, mobile, and call-center intake. Today, every claim is routed to a first-available adjuster regardless of size or risk profile, which means a $400 windshield claim and a $38,000 suspected-arson claim enter the same queue. Investigation capacity in the Special Investigations Unit (SIU) is scarce and is currently allocated by adjuster judgment after initial review — a step that adds 2–5 days to claims that should be fast-tracked, and misses early fraud signals on claims that should be flagged immediately.

Goal: automatically triage every incoming claim within seconds of submission into one of three lanes — auto-fast-track, standard adjuster queue, or SIU investigation queue — using a fraud-risk score computed from claim, policy, and document features.

2. Chosen Approach

An event-driven pipeline: claim submission triggers document ingestion, which triggers feature extraction, which triggers a call to an external AI risk-scoring service, which triggers rules-based routing. Each stage is a separately deployable service communicating over an internal event bus, persisting its own state, and independently testable.

Alternative consideredRejected because
Synchronous monolith call chain (intake API calls scoring directly, in-request)Ties claim-submission latency to a third-party scoring SLA; one slow vendor call blocks the whole intake API
Build fraud scoring in-house from scratchOutside the 20-week delivery window and duplicates a capability Meridian’s existing AI vendor already provides under contract
Batch nightly scoring instead of real-timeDefeats the purpose — SIU needs same-day signal on high-risk claims, not next-day

3.2 Size Discipline

UnitSoft targetHard ceiling
File~300 lines500 lines
Function~50 lines100 lines
Module export surface5–7 public symbols12

Touching an oversize file is the trigger to split it — not a reason to avoid touching it.

3.3 Types & Contracts

  • No any without a one-line comment explaining why it’s unavoidable.
  • Every exported function has an explicit return type — never inferred silently across a module boundary.
  • Inbound HTTP payloads validated with Zod before reaching business logic; malformed input returns 400, never reaches a service function.

3.4 Comments

Default to no comments. Add one only when it explains a non-obvious why — a workaround, a hidden constraint, a regulatory reason a threshold is set where it is. Never restate what the code already says.

Unnecessary

// increment the retry counter
retryCount++;

Earns its place

// Vendor SLA guarantees recovery within 3 attempts;
// a 4th retry only masks a real outage (see CS-TDD-001 §6)
if (retryCount >= 3) throw new ScoringServiceUnavailableError();

3.5 Logging

Structured JSON only. Every log line includes timestamp, level, service, event, correlation_id, and outcome. Never log a raw error object without a classified error_class. Never log a secret — API keys are redacted at the log-formatter level, not by convention.

6.1 Branching Model

Trunk-based development with short-lived feature branches. main is always deployable. No long-running develop branch — branches live hours to a few days, not weeks.

Branch prefixUseExample
feature/New capability, ticket-linkedfeature/CS-118-siu-threshold
fix/Bug fixfix/CS-142-duplicate-notification
chore/Non-behavioral (deps, config, refactor)chore/CS-155-split-routing-engine

6.2 Pull Request Rules

  • Size: soft target under 400 lines of diff. Larger PRs are split by the author before review, not reviewed as-is.
  • Reviewers: minimum 1; 2 required for changes touching riskScoringClient.ts or routingEngine.ts (CODEOWNERS-enforced).
  • CI gate before review starts: tsc --noEmit, lint, unit tests, coverage threshold (≥80% on touched files).
  • Merge strategy: squash-merge; commit message states the why, references the ticket.
  • SLA: first review response within 4 business hours.

6.3 Commit Message Convention

<type>(<scope>): <why, not what>

feat(routing): auto-fasttrack claims under $2,500 with risk < 20
fix(notification): dedupe by (claimId, type) to stop double-sends
chore(scoring): split riskScoringClient.ts at 520 lines
