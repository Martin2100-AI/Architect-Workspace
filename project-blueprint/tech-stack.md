# Tech Stack: Warranty Claim Triage

Based on [architecture.md](./architecture.md).

| Component | Recommended Tech | Fit | Why | Learn more |
|---|---|---|---|---|
| Claim Submission Form | Next.js (React) | 🟢 great fit | A customer form plus a status page is exactly what Next.js's file-based routing and easy hosting handle well, letting a 2-person team ship without a separate frontend build pipeline. | `Explain Next.js to me like I'm new to frontend frameworks, using my project as the example.` |
| Claims API | Next.js API Routes | 🟢 great fit | At a handful of synchronous claims per day, a standalone backend service (serverless = code that runs without you managing a server) would add deployment and networking overhead with no payoff, so keeping the API in the same app as the form is simpler and just as capable. | `Explain Next.js API Routes to me like I'm new to backend APIs, using my project as the example.` |
| Purchase and Warranty Database | PostgreSQL (hosted via Supabase) | 🟢 great fit | Purchases, warranty terms, and claim decisions are relational data with real cross-references, which is what a SQL database is built for, and a managed service (someone else runs the server for you) removes database upkeep for a team with no dedicated infra person. | `Explain PostgreSQL and Supabase to me like I'm new to databases, using my project as the example.` |
| Claim Extraction and Matching Engine | Anthropic Claude API (text, with vision if photos need analysis) | 🟡 good fit | It reads free-text descriptions and photos without training a custom model, but each claim costs a metered API call and its output must stay advisory only — the Decision Engine, not the model, makes the final auto-approve call, per the project's "ask a human over guess yes" rule. | `Explain the Anthropic Claude API to me like I'm new to AI models, using my project as the example.` |
| Auto-Approval Decision Engine | Plain TypeScript rules module (hand-written, no rules-engine library) | 🟢 great fit | The three checks (in-window, matched purchase, matched defect) are simple boolean logic; reaching for a business-rules engine (BRMS = a platform for managing rules outside code) would only hide the exact logic that has to stay auditable for a component whose entire job is not guessing. | `Explain writing simple business rules in plain TypeScript to me like I'm new to backend logic, using my project as the example.` |
| Agent Review Dashboard | Next.js admin page (role-gated route in the same app) | 🟢 great fit | Two known reviewers don't need a dedicated low-code app platform; reusing the existing frontend keeps the whole system in one deployable and avoids a new vendor bill for a 2-person audience. | `Explain building a simple role-gated admin page to me like I'm new to internal tools, using my project as the example.` |
