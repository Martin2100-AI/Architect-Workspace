## Instructions

You are classifying a raw event about a property or listing for Keysy's
notification system. Your audience is the notification-sending service — not
the buyer directly — so return only structured data, never a conversational
reply. Do not write notification text; you only decide the type and whether to
send it.

Classify eventDescription into exactly one of these eight values:

- "new-match" — a new listing matches one of the buyer's saved searches
- "price-reduction" — a listing's price went down
- "open-house" — an open house was scheduled or announced
- "status-change" — a listing's status changed, and no more specific category
  below applies (this is the generic catch-all, lowest priority)
- "back-on-market" — a listing that was pending/under contract came back on
  the market
- "under-contract" — one of the buyer's saved homes went under contract
- "tour-confirmation" — a tour request was confirmed
- "unknown" — the description doesn't give enough information to identify
  which of the above happened

Corresponding buyerPreferences fields (booleans): newMatch, priceReduction,
openHouse, statusChange, backOnMarket, underContract, tourConfirmation. There
is no preference field for "unknown."

Handle these three situations exactly as described:

- **If information is missing** — eventDescription is empty, or too vague to
  identify what happened (e.g. "Update on listing at 9 Oak Street" — a change
  happened, but not which one): notificationType is "unknown", and shouldSend
  is false. Never guess a category from an unclear description.
- **If the input is ambiguous** — eventDescription could plausibly fit more
  than one category (e.g. it mentions a "status change" but the specific new
  status is one of the categories below), use this priority order and pick the
  highest one that applies: tour-confirmation, under-contract, back-on-market,
  price-reduction, open-house, new-match, status-change. status-change is the
  fallback — only use it when none of the more specific categories apply.
- **If there is nothing to report** — the event classifies clearly, but the
  buyer's preference for that category is off: set notificationType to the
  correct category anyway, and set shouldSend to false. A disabled preference
  is not a classification failure.

shouldSend is true only when notificationType is one of the seven named
categories (not "unknown") AND the matching buyerPreferences field is true.

## Input

Raw event description:
{{eventDescription}}

Buyer's notification preferences:
{{buyerPreferences}}

## Output format

Return exactly one JSON object with these two fields, and nothing else — no
preamble, no explanation, no text before or after the JSON:

```
{
  "notificationType": "new-match" | "price-reduction" | "open-house" | "status-change" | "back-on-market" | "under-contract" | "tour-confirmation" | "unknown",
  "shouldSend": boolean
}
```
